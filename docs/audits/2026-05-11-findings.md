**Task 13 audit result: lock files are NOT created by VXD code. Root cause is fully upstream.**

### What Was Found

The `locks/` directory and its 341 entries were created by an **unknown tool or session** that ran on May 7–10, 2026 and had write access to `~/.mempalace/`. The naming pattern (16 hex chars, 0 bytes) matches transaction-sentinel patterns used by some database or job-queue systems, but the exact creator could not be identified by static analysis of installed Python packages, the ChromaDB Rust binary, or VXD source code.

### Two Distinct Failure Periods

#### Period 1: April 9–19 (51 `aborted` entries)

Compounding this: `ANTHROPIC_API_KEY` was set in the shell environment. The CLI adapter did not strip it, so Claude used API credits instead of the Max subscription — hitting billing errors before even reaching the 1-turn limit.

**Critical data gap:** The old `main.go` captured `result.Error` in `ImplementResult` but **did not pass it to `auditLog.Append()`**. All 51 aborted entries in the changelog have empty `error` fields. The errors existed at runtime but were never persisted. This is why the Task 7 audit found aborted entries with no visible failure reason and concluded the root cause was "unclear."

The fix was committed on April 19, 2026 in commit `9bb5c07`:
- `--max-turns 1` → `--max-turns 25`
- Added `llm.FilterClaudeEnv(os.Environ())` to strip `ANTHROPIC_API_KEY` + `CLAUDECODE`
- Added `Error: result.Error` to `auditLog.Append()`
- Added the `actionable` filter (see Period 2)

#### Period 2: April 20 – May 11 (19 `proposed` entries, 0 `aborted`)

**Root cause: All scored findings are non-actionable by design — the triage filter is working correctly**

After the April 19 fix, the `actionable` filter was added. Gemma 4 evaluates each finding and returns `"actionable": false` for competitor intelligence, LLM provider news, and ecosystem release notes — which is **exactly the right call** for those sources.

Looking at all 19 `proposed` entries in this period:
- `llm_providers` (8 entries): Anthropic Newsroom, OpenAI News, Ollama releases — these are news items, not code changes
- `competitors` (6 entries): OpenHands, SWE-agent releases — competitive intelligence, not actionable code changes
- `go_ecosystem` (3 entries): Go Blog, Go Release History — ecosystem updates, not specific action items
- `security` (2 entries): Go Vulnerability Database — Gemma correctly flagged these as proposed (the GoVulnDB page requires a specific CVE to be actionable; a generic scrape yields no action)

The disposition label `proposed` means "this is intelligence worth reading, but not a code change." The pipeline runs correctly since April 20; it just hasn't seen a finding that Gemma marks actionable for VXD's codebase.

**Run summary confusion:** The existing audit text described `proposed` entries as "findings marked actionable but not implemented." This is incorrect. The `proposed` path in `main.go` (line 102–117) is explicitly triggered by `!sf.Actionable` — these are *non-actionable* findings logged for the email report. The `prs_proposed` counter in `RunSummary` is misleading nomenclature; it counts "intelligence findings we're reporting on" not "findings we tried to implement."

### Is the Zero-PR Rate a Bug or Design Intent?

It is **both, in sequence**:

1. **April 9–19: genuine bug** — `--max-turns 1` + billing conflict caused all implementation attempts to fail silently. This is now fixed.
2. **April 20 onward: correct behavior** — the pipeline runs daily, scrapes 14 sources, and finds only competitor news and ecosystem releases. Gemma correctly marks these non-actionable. No actionable findings → no PRs. The pipeline is doing what it was designed to do.

The original audit CRITICAL severity was based on seeing "51 aborted / 0 merged" and concluding implementation was broken. That was accurate for the April 9–19 period. For April 20 onward, the label `aborted` never appears — the pipeline correctly classifies and logs everything.

### Why No Actionable Findings Appear

The 14 scraped sources (`currentSources` in `research.go`) are almost entirely:
- Competitor GitHub releases (OpenHands, SWE-agent, Dagger, AutoGen, CrewAI, Aider)
- LLM provider news (Anthropic, OpenAI, Google AI, Ollama)
- Ecosystem news (Go Blog, Go releases, HN Best, GitHub Trending)

These sources produce **awareness content**, not **code-actionable signals**. A release note for OpenHands does not tell VXD what to implement. The `deep-dive` daily topic (one of 8 rotating topics: event sourcing, AI orchestration, CLI UX, Go performance, etc.) has better potential for actionable findings, but Gemma's triage appears to be conservative — it rates deep-dive findings as relevant but still non-actionable unless there is a specific concrete action to take.

### Recommended Follow-Up (Feature Request, Not Bug)

The pipeline was designed around external research (what are competitors doing, what are LLMs releasing). For PRs to actually be created, the pipeline needs sources that generate **internal code-actionable signals**:

1. **Add internal code analysis sources** — e.g., run `golangci-lint` on the codebase and feed real lint findings into the triage loop. A finding like "G304: file path provided as taint input" in a specific file IS actionable by the implementer.
2. **Add `go test ./... -race` failure parsing** — test failures are strongly actionable and well-scoped.
3. **Add `govulncheck` output** — specific CVE hits in dependencies are actionable (upgrade the dep).
4. **Tune deep-dive actionability** — the 8 rotating deep-dive topics could be made actionable by requiring Gemma to output a specific code suggestion, not just a relevance score.

None of these require loosening the triage filter (which would increase noise). They require adding better input sources.

### Code Fix Applied

The old `main.go` did not persist errors to the audit log. This was already fixed in `9bb5c07` for new runs, but the **existing 51 aborted entries in `changelog.jsonl` have permanently empty error fields** — the runtime errors were never captured.

No additional code change is needed for the core bug. The fix already shipped. This task's deliverable is the diagnosis above.

**Wiring test gap:** There is no test that verifies `result.Error` is passed to `auditLog.Append()`. If someone refactors `main.go` and drops the `Error:` field, the silent-failure mode returns. A wiring test is added to guard this path.

### Wiring Test Added

Added `TestWiring_ImplementerError_PersistedToAuditLog` in `internal/improve/implementer_test.go` to verify that when the implementer returns an error, the error string is included in the `AuditEntry`. This test exercises the contract between `ImplementResult.Error` and the audit log call site.
