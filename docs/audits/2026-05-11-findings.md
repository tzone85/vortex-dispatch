**Detailed findings:**

**SH-1 — registry.go: `promptFile` and `cfg.LogFile` paths interpolated into shell string without `QuoteShellArg`**
- File: `internal/runtime/registry.go:158,163`
- Code: `cmdStr = fmt.Sprintf("%s -p \"$(cat '%s')\"", cmdStr, promptFile)` and `cmdStr += fmt.Sprintf(" 2>&1 | tee '%s'", cfg.LogFile)`
- `promptFile` is derived from `cfg.WorkDir` + `".vxd-prompts/prompt.txt"` where `WorkDir` comes from `filepath.Join(worktreeBase, a.StoryID)`. `StoryID` is generated from `reqID + role + counter` via `dispatcher.go:114` — fully internal, not attacker-controlled.
- `cfg.LogFile` is similarly system-generated under the VXD state directory.
- **In the current threat model** (VXD is a local developer tool, not a multi-tenant service) these paths are generated by VXD itself and do not accept external input. Exploitation would require compromising the state directory path first.
- However, `QuoteShellArg` exists precisely for this pattern and is not being applied here. If `WorkDir` or `LogFile` ever accepted user-supplied paths (e.g., via `vxd.yaml` `workspace.state_dir`), this becomes an injection vector.
- **Severity:** MEDIUM — theoretical in current single-user deployment; would become HIGH if `state_dir` accepted adversarial input.

**SH-2 — web/handlers.go: `sessionName` passed to `exec.Command("tmux", "kill-session", "-t", sessionName)` without `ValidateSessionName`**
- File: `internal/web/handlers.go:275`
- `sessionName` is looked up from the projections store by `agentID`. `agentID` is validated via `agentIDPattern` (`^[a-zA-Z0-9_-]+$`) before the store lookup. `SessionName` in the store is set from event payloads where the value originates from `dispatcher.go:114` (`fmt.Sprintf("vxd-%s-%s-%d", reqID, role, agentCounter)`).
- The path from external input to `sessionName` goes through two layers of indirection (WebSocket payload → store lookup → projection). Direct injection would require compromising the event store.
- `ValidateSessionName` is defined and tested but never called anywhere (confirmed by deadcode scan). Using it here would add defense-in-depth.
- **Severity:** LOW — two layers of indirection protect this path; `ValidateSessionName` should still be applied per the existing defensive pattern.

**SH-3 — autoresearch/metric.go: user-configured `Metric.Command` executed via `sh -c`**
- File: `internal/autoresearch/metric.go:38`
- Code: `exec.CommandContext(ctx, "sh", "-c", h.Metric.Command)`
- `Metric.Command` is a user-defined metric script from `vxd.yaml` (e.g., `autoresearch.metric.command: "go test ./... | tail -1"`). This is by design — users author the metric command and it runs in the worktree.
- This is the documented autoresearch design, not a vulnerability. The attack surface is local `vxd.yaml` modification, which already requires filesystem access.
- **Severity:** INFO — intentional design; noted for completeness.

**SH-4 — runtime/ssh_runner.go: `pe.Command` and `sessionID` interpolated into remote shell string**
- File: `internal/runtime/ssh_runner.go:71,80`
- `pe.Command` (`PreparedExec.Command`) is assembled by `CLIAdapter.Prepare()` and validated via `ValidateShellArg` on all extra args. The command string itself is protected by `%q` formatting in `Sprintf` (Go's `%q` produces a double-quoted, backslash-escaped string). `sessionID` in `Terminate()` uses `%q` similarly.
- `%q` provides strong protection for these cases by escaping shell-significant characters.
- **Severity:** LOW — `%q` quoting provides adequate protection; no immediate exploit path.

**Severity summary:** 0 CRITICAL, 0 HIGH, 1 MEDIUM (SH-1), 2 LOW (SH-2, SH-4), 1 INFO (SH-3).
